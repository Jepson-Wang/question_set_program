# Task 9 开发需求：画像候选池（频次确认）

> 对应计划：`docs/superpowers/plans/2026-09-08-memory-architecture.md` 的 Task 9
> 前置：Task 8（画像 JSON 合并写入 + notes 逃生口）已完成，提交 `0503563`

---

## 一、要解决的问题

Agent 分不清这两句话的区别：

| 用户说 | 性质 | 正确处理 |
|---|---|---|
| 「这题再简单点」 | 一次性诉求 | 本轮响应即可，**不应**进长期画像 |
| 「以后题目都简单点」 | 稳定偏好 | 应当沉淀进长期画像 |

现在 `UserProfileSaveTool` 把模型传来的所有字段一股脑写库。一次性诉求一旦进了画像，会污染**此后每一次**请求。

Task 8 刚把画像写入从「整体替换」改成「合并」，这让污染变成只增不减 —— 错误的偏好再也不会被后续写入覆盖掉，只能人工清理。所以频次确认这一层，在 Task 8 之后变得更必要，而不是更可选。

靠提示词约束模型自己判断，准确率不够。

---

## 二、解决思路

**用统计代替判断。** 字段按性质分两类：

| 类别 | 字段 | 写入时机 |
|---|---|---|
| 事实类 | `grade`、`subject` | 第一次就落库 |
| 自由观察 | `notes` | 第一次就落库 |
| 偏好类 | `weak_points`、`preferences` | 进候选池，**同一字段路径第二次出现**才晋升入库 |

`grade` / `subject` 是事实陈述（「我初二」），`notes` 是自由观察，两者都不存在「一次性 vs 稳定」的歧义，不需要频次确认。

**代价**：偏好生效滞后一轮。换来的是判定不再依赖模型的主观发挥。

### 这里绕开了一个难题

「两次说的是不是同一个偏好」本来需要语义相似度计算。但 LLM 在提取时**已经把偏好结构化成了字段名**，所以同键即同偏好，比较字符串就够了。

**前提是键名受控** —— 这由 Task 10 的词表保证。在 Task 10 落地之前，模型自造键名会导致计数永远累积不到阈值、偏好静默失效。这是已知且接受的临时状态，但必须在工具描述里写明。

## 三、需求清单

### 需求 1：新增候选池组件

**位置**：`backend/agents/memory/profile_candidates.py`（新建）

**职责**：记录「某用户的某个字段路径被提议过几次」，并在达到阈值时告知调用方可以晋升。

它**只负责计数，不负责落库**。落库归属见第五节。

**存储**：Redis hash，一个用户一个 key。

- hash 的 field 是**字段路径**，形如 `字段名.子键`（例如 `preferences.题目风格`）
- hash 的 value 需要能还原出：当前值、累计次数、首次出现时间

**需要对外提供的能力**：

| 能力 | 输入 | 输出 |
|---|---|---|
| 提交一个候选 | 用户 ID、字段名、子键、值 | 当前计数 + 是否达到晋升阈值 |
| 读取该用户全部候选 | 用户 ID | 字段路径 → 记录 |
| 清空该用户候选 | 用户 ID | — |

**可配置项**：过期时间（默认 7 天）、晋升阈值（默认 2）。两者都要能在构造时覆盖。

**行为约束**：

1. 同一字段路径重复提交，计数累加
2. 同键值冲突时**以新值为准**
3. 不同字段路径**各自独立计数**，互不影响
4. 达到阈值时，该候选项要被**清除**，避免同一个偏好重复晋升
5. 每次写入都要刷新整个 key 的过期时间
6. 字段名取值只限 `weak_points` 和 `preferences`

---

### 需求 2：改造 `UserProfileSaveTool`

**位置**：`backend/agents/tools/user_profile_save_tool.py`（修改）

**入参 schema**：补上 `notes` 字段（可选的字符串数组）。

Task 8 已经打通了 `notes` 从 schema 到 MySQL 的完整链路，但这个工具还没有这个入口，所以模型目前根本没法写 notes。

**写入逻辑**：

- `grade`、`subject`、`notes` —— 直接进写库集合
- `weak_points`、`preferences` —— **逐个子键**过候选池，只有晋升的那些才进写库集合
- 写库集合非空时才调用 LTM 写入

**返回文本必须如实汇报**，至少包含两部分：

- 这次实际写入了哪些字段
- 哪些还留在候选池里，以及进度（例如 `题目风格（1/2）`）

这一条不是锦上添花。**汇报不实，Agent 会以为偏好已经生效，转头就告诉用户「已经记住了」** —— 用户下次发现没生效，会认为系统在撒谎。

**工具描述（`description`，给 LLM 读的）要说明**：

1. 年级、学科、notes 立即生效
2. 薄弱知识点和长期偏好需要在**不同轮次**出现两次才会写入
3. 两者的键名必须取自 `profile_schema` 词表（Task 10 提供）
4. **自造键名的后果**：频次永远累积不到阈值，偏好静默失效
5. 确实没有合适的键时，写进 `notes`，不要新造键

第 4 条要写得足够直白 —— 模型看不到后果就不会遵守约束。

## 四、边界与容错要求

### 1. Redis 不可用时不能阻断主流程

候选池读写失败要**记日志并当作「未达阈值」处理**，让用户的请求照常完成。

画像写不进去是可以接受的降级；因为画像写不进去导致整个对话失败，不可接受。

### 2. 「提交候选」不是原子操作，这是有意的

它是读 → 改 → 写。同一用户的两个请求并发进来时，可能各自读到相同的计数，最后都写成同一个值，**少计一次**。

后果只是偏好晚一轮生效，可以接受。

**注意这和短期记忆的取舍正好相反**：那里丢的是用户消息，所以必须用 Lua 保证原子。这里丢的是一次计数，代价小得多。要严格的话可以改成 `HINCRBY` 或一小段 Lua，但不是必须。

### 3. 晋升后「先删候选、再写库」

达到阈值时会立刻清除候选项，如果紧接着写库失败，**这次晋升就丢了**，用户得再说一遍。

想更稳妥可以改成写库成功后再删 —— 代价是写库成功、删除失败时会重复晋升一次。两种都可以，但要知道自己选的是哪种。原因见下一节。

## 五、落库归属：候选池不碰 MySQL，谁碰？

候选池只回答一个问题：**「这个偏好够不够格进画像」**。它不知道、也不该知道 `user_profile` 表长什么样。

真正的落库链路不变，仍然是 Task 8 那一条：

```
UserProfileSaveTool._arun        ← 编排层：收集晋升结果，决定写什么
        │
        ▼
LongTermMemory.add_or_update     ← 领域层：画像不存在则新建，存在则局部更新
        │
        ▼
UserProfileMapper                ← 数据访问层：create_memory / update_user_profile
        │
        ▼
      MySQL  user_profile
```

**候选池挂在最上面那一层的旁边，不在这条链路里。** 工具拿到「晋升了」的信号后，把这些子键收进写库集合，和 `grade` / `subject` / `notes` 一起，走同一次 `LTMRequest` 写下去。

这样分的三个理由：

1. **两种存储的语义不同。** Redis 里的计数是可丢失的短时状态（7 天过期、Redis 挂了就当没有）；MySQL 里的画像是持久事实。把它们塞进一个组件，就得同时承担两套可靠性要求。
2. **候选池不需要知道画像的结构。** 它只处理「字段路径 → 计数」这一个抽象。`user_profile` 加列、改表、换数据库，都不该影响它。
3. **Task 10 要在中间插一层。** 词表分流会插在工具里，位于「模型传入」和「进候选池」之间。工具是编排层，插得进去；候选池如果自己写库，这个插入点就没了。

### 由此带来的那个缝

「晋升」发生在 Redis（删候选），「落库」发生在 MySQL（写画像），**中间没有事务**。两个存储之间不可能有跨库事务，所以只能二选一：

| 顺序 | 失败时的后果 |
|---|---|
| 先删候选，再写库 | 写库失败 → 这次晋升丢了，用户得再说一遍 |
| 先写库，再删候选 | 删除失败 → 下次再提这个偏好会重复晋升一次（写库是幂等的合并，实际无害） |

计划里选的是前者。后者其实更稳妥一些 —— 重复晋升写的是同一个键同一个值，经过 Task 8 的合并逻辑之后是幂等的，损失比「丢晋升」小。实现时可以按后者做，但要在注释里写清楚选的是哪种、为什么。

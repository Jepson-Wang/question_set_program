# RAG 知识库接入设计

日期：2026-09-11
状态：已确认，待实施
范围：新建 `backend/agents/rag/`、`backend/api/manage_api/rag_api.py`；修改生题链路（`question_set_tool` / `question_set_agent`）、启动钩子与 skill 加载器

---

## 背景与目标

生成变式题目前完全依赖模型的自身知识：没有参考真题做风格与难度锚点，也没有教材原文保证知识点表述准确。`backend/agents/rag/` 是一个空包，仓库里没有任何语料。

目标：
1. 建立题库与教材两个知识库，支持 PDF / Word 资料导入与 LLM 批量生成种子题
2. 生成变式题前先检索：多路召回 → 融合 → 重排 → Top-K，整理成参考材料交给生题模型决策
3. 由第三方模型把守入库质量，并用离线评测量化每一项检索技术的实际收益

## 关键决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 语料来源 | PDF / Word 资料 + LLM 生成，题库与教材分库 | 仓库目前零语料，两种来源都要支持；题目和讲解的检索方式与用途不同 |
| 第三方模型评估的位置 | 入库闸门 + 离线评测 | 线上请求路径零额外延迟；错题不入库比事后纠正便宜得多 |
| 入库入口 | 命令行 + 管理后台接口，共用同一个服务层 | 开发期用命令行，运营期用后台，逻辑只写一份 |
| 多路召回的存储 | Chroma + 进程内 BM25（方案 A） | 零新增服务，匹配单机单进程部署；每一路独立可测，便于消融评测 |
| 重排 | DashScope 文本排序服务，接口可替换 | 本地 cross-encoder 需要 torch，当前 Python 3.14 环境已有编译扩展兼容问题；CPU 推理也慢 |
| 裁判模型 | 独立配置，强制与生成模型不同家族 | 同家族模型会系统性地偏向自己的输出，失去复核意义 |

## 被否决的方案

- **Milvus 原生混合检索**：一次请求完成稠密 + BM25 检索、内置 RRF，一致性由数据库保证。但要多跑一个服务（Windows 开发机基本依赖 Docker），中文分析器与适配器支持需要先验证。语料为零的阶段过重。召回层做成接口，规模上来后可以迁移。
- **Elasticsearch + Chroma**：全文检索最成熟，但要多维护一个重型服务并在两套存储间同步，三者中最重。
- **线上生成闸门**：每次生题后实时由第三方打分、不合格重试。每个请求多一次 LLM 调用（2-5 秒与一份成本），裁判误判还会引发重试风暴。

## 一、数据与存储

**独立的库目录** `RAG_DB_DIR`（默认 `backend/rag_db`），不与记忆库 `vector_memory` 混放：知识库可以随时删掉重建，用户记忆删了就找不回来。所有目录都相对 `backend/` 解析，不依赖当前工作目录。

**两个 collection：**

| collection | 内容 | 粒度 |
|---|---|---|
| `rag_questions` | 题目：题干、答案、解析、题型、难度、知识点、年级、来源 | **一题一文档，不切块**——题目被切开就废了 |
| `rag_knowledge` | 教材讲解：概念、公式、方法 | 由结构化步骤按语义切成不超过 400 字的段 |

**文档 id = 前缀 + 规范化文本的 sha1。** 规范化做全角转半角、去空白、小写。同一道题无论来自哪份资料、第几次入库，id 都相同：重复入库天然幂等，精确去重只需比较 id。

**向量全部归一化为单位长度，Chroma 使用 cosine 空间。** 这样余弦相似度 = 点积，内存实现与 Chroma 给出的相似度可直接比较，阈值（近似去重、防泄漏）在两种实现下含义一致。

**词法索引**是一个进程内组件，同时承担三件事：
- BM25 关键词召回（jieba 分词 + rank_bm25）
- 知识点倒排表（知识点 → 题目 id）——Chroma 的 metadata 只接受标量值，无法可靠地做「列表包含某项」查询，所以元数据召回不依赖 Chroma
- 题目目录（id → 完整题目）——融合后的候选可以直接取出完整内容，不再回查向量库

rank_bm25 不支持增量添加，只能整体重建。**重建时先在旁边建好一份完整快照，再用一次赋值替换引用**；检索方法开头只读一次快照引用，读到的永远是完整一致的一份。与记忆模块「用数据结构消除竞态」同一思路。

使用独立的 `jieba.Tokenizer` 实例而非全局 jieba，词典改动不会波及进程里的其他代码。

**索引与查询都用 jieba 的搜索引擎模式（`cut_for_search`），它同时产出整词与子词。** 这一点是实施前验证时发现的：最初设计用普通分词、并把知识点名称加进词典保证整词，结果「分解因式 x²-9」与「因式分解：x²-9」两两之间除了 `x`、`²`、`9` 没有任何共同 token，同一知识点的不同说法互相召回不到；「鸡兔同笼问题」与「鸡兔同笼，头 35 个」同理。搜索引擎模式下两边都有「分解」「因式」「鸡兔」，而整词「因式分解」「一元二次方程」照样产出，使用标准术语的题目仍会额外得分。入库时出现的知识点名称依旧会加进词典，让它们作为整词出现。

**MySQL 两张表：**
- `rag_ingest_job`：入库任务（类型、状态、来源、参数、报告、错误）
- `rag_quarantine`：复核未通过的题目（完整字段 + 裁判结论 + 人工处理状态）。放 MySQL 而不是 Chroma：它是工作流状态，不是检索数据

## 二、入库流水线

```
PDF/Word → 加载 → LLM 结构化 ─┐
                              ├→ 精确去重 → 向量化 → 近似去重 → 第三方复核 ─┬→ 写入向量库 → 重建词法索引
LLM 按知识点生成种子题 ────────┘                                           └→ 隔离区（等人工复核）
教材讲解段 → 精确去重 → 向量化 → 写入教材库（不经复核）
```

**加载**：pypdf 按页提取文字层；python-docx 按文档顺序读段落与表格，累积约 1500 字切成一「页」。平均每页文字少于 20 字的 PDF 判定为扫描件，直接拒收并给出明确提示——这次不做 OCR，与其悄悄入库一堆空内容，不如明确报错。

**结构化**：LLM 按页面滑动窗口读取（每次 2 页，相邻窗口重叠 1 页），跨页的题目至少会在某个窗口里完整出现。只输出题干与答案都完整的题；答案集中印在书末、无法在同一窗口内确定对应关系的，不输出。重叠带来的重复靠 id 去重；同一道题在两个窗口里转写得略有不同的，由近似去重兜住。

**种子题生成**：按「知识点 + 年级 + 难度 + 数量」批量生成，每次调用最多 10 道。

**去重都放在复核之前**：重复的题不值得再花一次裁判调用。近似去重阈值为余弦相似度 0.95，与库中已有题目、同批次已接受的题目两边都比。

**第三方复核（入库闸门）**：
- PDF 里抽出的题**同样要复核**，不只是 LLM 生成的。教辅的答案经常集中在书末，结构化时容易配错。
- **裁判先独立解题，再与给定答案比对**，而不是被问「这个答案对不对」——后一种问法会诱导模型附和。
- 四项检查必须全部通过：答案一致、题干完整、不超出年级范围、知识点标注准确；且总分不低于 `RAG_JUDGE_PASS_SCORE`（默认 0.8）。布尔项必须是真正的 `true`，字符串 `"true"` 也算不通过。
- **失败即拒（fail closed）**：裁判调用失败或输出无法解析时，题目进隔离区而不是放行。闸门的意义就在于不确定时不放行。
- 复核并发上限 4（可配置）。

**教材讲解不经复核**：它来自权威原文而非生成。其知识点标签由 LLM 标注，标错只影响检索质量，由离线评测发现。

**裁判模型家族校验**：取模型名开头的字母段作为家族（`qwen-plus`、`qwen3-max` → `qwen`；`glm-5` → `glm`），并处理少量别名（`moonshot` → `kimi`）。与 `MODEL_NAME` 同家族时拒绝构建裁判。这是启发式规则，目的是拦住明显的配置错误。

**prompt 以 SKILL.md 形式存放**，复用现有热加载机制。新增 frontmatter 字段 `visibility: internal`：标记为 internal 的 skill 可以被代码 `load_skill`，但不出现在 ReAct 主提示词的 Skill 清单里，也不参与触发词匹配——否则 Agent 会看到「rag_judge」这类与用户请求无关的能力包并尝试加载。

## 三、检索链路

```
查询 = 原题 + extract 得到的知识点与难度 + 用户年级（来自长期画像）
  ├─ 向量召回    top 20 ┐
  ├─ BM25 召回   top 20 ├→ RRF 融合 top 30 → 防泄漏过滤 → 重排 → top 3（低于阈值丢弃）
  └─ 知识点召回  top 20 ┘
  并行：教材库向量召回 top 2（相似度不低于 0.5）
```

- **三路召回并行执行。** BM25 与 PDF 解析等 CPU 工作投递到记忆计划 Task 3 建立的向量库专属线程池。
- **知识点召回**：按与查询知识点的重合数排序，难度一致加 0.5 分；已知用户年级时过滤掉更高年级的题目。
- **RRF 融合**：`score(d) = Σ 1 / (60 + rank)`。只看名次不看原始分数——BM25 分数、余弦相似度、知识点重合数三者量纲不同，无法直接相加。
- **防泄漏**：用户问的这道题本身可能就在题库里。候选的 id 与查询相同，或与查询的余弦相似度不低于 0.95 时排除，否则模型会把「参考真题」原样照抄回去。
- **重排**：DashScope 文本排序服务，对融合后的候选打分，取前 3 且分数不低于 0.3。接口的地址、模型名与响应结构在实施的第一个任务里用真实请求确认，不凭记忆写。
- **逐级降级**：任何一路召回失败就跳过该路；重排失败退回融合顺序；向量化失败则只剩不需要向量的两路；全部失败返回空结果。RAG 是增强，不是依赖，生题照常进行。
- 每个阶段记录耗时，目标是生题请求因 RAG 增加的 p95 延迟不超过 800ms。

## 四、接入生题

- `question_set_tool` 在 extract 之后调用检索，把结果整理成「参考真题」与「相关知识点」两段，拼进生题的 system prompt，总长度不超过 1200 字，超出时整条丢弃靠后的条目，不截断半条。
- 附带使用规则：**参考题型、难度与考法；不得照抄题干或数字；参考题与原题知识点不一致时忽略它。** 怎么用由模型自己决定。
- **防照抄检查**：以参考题干为基准，计算其字符按顺序出现在生成结果中的比例，**不低于 0.9** 即判定照抄，带上「与参考真题过于相似」的提示重试一次；重试后仍相似则记警告并原样返回。
  - 阈值取 0.9 而不是更低，是实测出来的：参考题与原题常是同一类题型，模型老老实实给原题换数字，结果与参考题的相似度本来就在 0.85 左右（「鸡兔同笼，头30个，脚80只」对「头35个，脚94只」），0.8 会误伤这类正常的变式题。0.9 只拦截几乎原样照搬的情况（原样 1.00，只改一个数字 0.95）。
- 各段在 system prompt 中的顺序：生题剧本 → 参考材料 → 用户偏好（记忆计划 Task 12 的向量记忆召回）。偏好放最后，作为最终的风格约束。
- **依赖记忆计划 Task 12**：它为 `question_set_tool` 注入 `user_id` 并加入记忆召回，本设计在其基础上扩展。
- `RAG_ENABLED=false` 时整条检索链路关闭。

## 五、管理后台接口

挂在项目里已有的 `manage_api` 路由（前缀 `/manage`）之下，自身前缀 `/rag`，最终路径 `/manage/rag/...`；`manage_api` 此前定义了但未接入 `main.py`，这次一并接入。全部接口要求 `user_privilege >= 1`。

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/upload` | 上传 PDF / Word，异步入库，返回任务 id |
| POST | `/generate` | 按知识点、年级、难度、数量生成种子题并入库 |
| GET | `/jobs/{job_id}` | 查询任务状态与入库报告 |
| GET | `/quarantine` | 列出隔离区条目（按状态筛选、分页） |
| POST | `/quarantine/{id}/approve` | 人工通过：跳过裁判直接入库 |
| POST | `/quarantine/{id}/discard` | 人工丢弃 |

- 上传文件**不使用用户提供的文件名落盘**，只用「任务 id + 已校验的后缀」，杜绝路径穿越。大小上限 20MB。原始文件名单独传给入库服务，写进题目来源——否则来源里记的就是一串任务 id，无法追溯。
- 裁判未正确配置时，上传与生成接口在创建任务之前就返回 503，不留下一个注定失败的任务。
- 入库任务在进程内后台运行，**同一时间只跑一个**：入库密集调用 LLM，词法索引重建也需要串行。
- 服务重启时，所有「待运行」「运行中」的任务一律标记为失败，不做断点续传。id 是哈希、入库是幂等的，重新提交即可，已入库的部分会被自动跳过。
- 关停时先等待在途任务（最多 10 秒），再关闭数据库连接、Redis 与线程池——任务还要用它们。

## 六、离线评测

**评测集（known-item 方法）**：从库中抽样题目，让 LLM 改写成「考法相同、措辞和数字不同」的新题作为查询，原题就是标准答案。改写失败、原样返回、或改写后与原题相似度不低于防泄漏阈值（会被检索主动排除）的样本在构建时剔除。也支持手工补充标注数据，格式相同。

**检索消融**：同一批查询分别用五种配置跑一遍——只用向量、只用 BM25、只用知识点、三路融合、融合加重排，计算 Recall@3/5/10、MRR、nDCG@5、p95 耗时与降级率，输出对比表。**「多路召回和重排到底有没有用」直接用数字回答。** 评测时关闭重排分数阈值，衡量的是排序质量本身。

**生题 A/B**：同一道题，有 RAG 与无 RAG 各生成一次，由裁判成对比较。**每对比较两次，交换两者的先后位置**：两次结论一致才算一方胜出，否则记为平局——位置一换结论就变，说明裁判没有真正的偏好，只是在偏向某个位置。输出胜 / 平 / 负比例。

报告写入 `RAG_EVAL_DIR`（默认 `backend/rag_eval`），Markdown 与 JSON 各一份。

## 已知限制（本次不做）

- **不做 OCR**：扫描件 PDF 拒收。图片形式的公式、几何图形无法提取。
- **Chroma 本地库不支持多进程同时写入**：服务运行期间请用后台接口入库；命令行入库完成后要重启服务，服务里的词法索引才会包含新题。
- **单机单进程**：任务执行器、词法索引都在进程内，多实例部署需要另行设计。
- **后台接口的测试依赖 chromadb 可导入**：`backend/api/__init__.py` 在包初始化时会导入全部路由，`agent_api` 导入时就要实例化向量库，因此导入 `backend.api` 下的任何模块都会连带导入 chromadb。这是项目原有的结构，本次不改；相关测试用 `importorskip` 守住，chromadb 不可用时明确跳过而不是报错。
- **规模上限**：词法索引常驻内存，每次入库整体重建。十万级题目以内没有问题，再往上应迁移到 Milvus。

## 验收标准

1. PDF 与 Word 资料可以通过命令行和后台接口入库；同一份资料重复入库，第二次的新增数为 0。
2. LLM 生成与 PDF 抽取的题目全部经过第三方复核；未通过的进入隔离区，可人工通过或丢弃。
3. 裁判与生成模型同家族、或裁判未配置时，入库拒绝执行并给出明确原因。
4. 裁判调用失败或输出无法解析时，题目进入隔离区而不是被放行。
5. 生题请求会检索参考题并注入 system prompt；用户问的原题不会作为参考题出现。
6. 任意一路召回、重排或向量化失败时，生题仍然正常完成。
7. 生成结果照抄参考题时会触发一次重试。
8. 离线评测能输出五种配置的检索指标对比表，以及有 / 无 RAG 的生题胜率。
9. 非管理员调用后台接口得到 403；上传文件不会写到上传目录之外。
10. RAG 的 skill 不出现在 ReAct 主提示词的 Skill 清单中。
